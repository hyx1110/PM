# 加班申请与实际执行

## 入口和审批

入口为 **任务执行 → 加班申请**，包含“我的申请”“由我审批”“相关申请”。指定审批人的首页“待处理事项 → 审批”同步展示加班待办，可打开抽屉批准或驳回。

| 情况 | 审批人 |
|---|---|
| 员工为自己参与项目的任务申请加班 | 对应项目的项目经理 |
| 项目经理为自己负责项目的任务申请加班 | 项目所属部门配置的部门主管 |
| 项目经理为自己作为成员参与的其他项目申请加班 | 该项目的项目经理 |
| 项目经理和部门主管恰好是同一人 | 禁止自己审批自己，须先配置另一名有效部门主管 |

部门主管须有效、属于项目部门并持有 `department_manager` 系统角色。申请保存时确定审批人；现有待办保留指定审批人，不因后续人员组织调整静默改派。停用/删除人员时会检查未结束加班依赖，须先处理申请。超级管理员可查看全局申请，但本功能不提供绕过指定审批人的代审批，以保证不自审。

“相关申请”对普通账号仅展示自己申请、指定由自己审批或自己负责项目的申请；超级管理员、部门主管按现有全局范围查看。查看权限不等于审批或撤回权限。撤回仅限申请本人。

## 业务流程

1. 员工选择自己参与、已审批且未结束项目中的本人末级任务。
2. 选择未来的非工作时间、填写原因；0.5h 为单位，申请日期不得超出任务计划范围。
3. 在加班开始前，由指定审批人批准或驳回；驳回须填写原因。过期未审批申请保留记录、不能再批准，可驳回或由本人撤回后重新申请。
4. 加班结束后，申请人在“我的申请”点击“填报执行”，系统带入任务、本人、日期及批准工时。
5. 填写实际发生的加班工时和执行说明，保存后才计入实际工时。实际工时可少于批准工时，但不得大于批准工时；以 0.5h 计。

当前加班以日为申请单位，可结束于当日 24:00（数据库保存为次日零点）；零点为右开区间边界，实际执行日期仍属于申请当天。跨日持续加班请按零点拆成两条申请。工作日历复用系统现有配置：工作日的 08:30–12:00、13:00–17:30 不可申请加班，午休、上班前、下班后及非工作日可申请。法定假日/调休必须已在系统工作日历数据中正确配置；未配置日期仍沿用周一至周五工作、周末休息的现有规则，不会自动联网获取节假日。

加班申请不创建 `schedule_bookings`，不出现在共享预约看板，不占用正常预约额度，不增加项目计划工时或预算。如果同时需要提高项目计划额度，仍走原“项目资源申请”。加班超出预计后，既有报表/首页工时偏差会正常反映实际超支。

## 工时和状态口径

- 实际工时总额 = 正常执行记录工时 + 已填报的加班执行记录工时；审批工时本身不是实际工时。
- 加班使用原 `execution_records` 表，通过 `overtime_request_id` 区分来源；列表显示“加班”标记，原报表、首页实际趋势、任务/项目实际时间汇总及执行导出的实际工时计算自动包含它。
- 执行明细导出末尾增加“工时来源”和“加班申请ID”，可区分正常工作与加班，原日期和工时列位置不变。
- 首页“计划工时”仍来自有效普通预约，不将加班申请加入计划预约趋势；实际趋势包含已发生、已填报的加班。这是口径差异，不是漏算。
- 同一加班申请只允许一条有效执行记录。填错时编辑原记录；软删除原记录后，申请可重新填报。
- 正常工作和加班须分两条记录填报，不要在正常记录中再次包含已独立填报的加班工时。
- 加班记录仍采用任务现有“进行中 / 已完成”执行状态，任务以最新有效执行记录联动；项目继续由负责人手动确认完成。
- 还有待审批或已批准但未填报的加班时，不能直接把任务/项目结案，须先填报、驳回或撤回相关申请。
- 有未填报加班时，不能将该任务转为汇总任务，也不能通过移除任务成员、收缩任务日期或删除任务使加班成为孤立数据。
- 本人可撤回待审批或已批准但尚未填报的申请；填报后须先按原执行权限删除记录。已结束/已评价项目遵循原执行记录锁定规则。
- 如果删除一条历史加班执行后，其他最新记录仍使任务保持“已完成”，须先将最新执行记录改回“进行中”再删除，避免申请无法重新填报。

## 数据和接口

迁移 `20260928_0017` 新增 `overtime_requests`，并增加 `execution_records.overtime_request_id`。旧执行记录该列为空，原正常执行预约前置校验不变；加班执行以已批准申请作为前置凭证，不要求在共享看板再预约。

| 方法 | 接口（前缀 `/api/v1`） | 说明 |
|---|---|---|
| GET | `/overtime` | 分页查询，`scope=mine/approvals/related`，可筛选 `pending/approved/rejected/withdrawn` |
| POST | `/overtime` | 当前用户申请，参数 `task_id/start_time/end_time/reason` |
| GET | `/overtime/{id}` | 权限范围内详情 |
| POST | `/overtime/{id}/approve` | 指定审批人批准，`note` 可选 |
| POST | `/overtime/{id}/reject` | 指定审批人驳回，`note` 必填 |
| POST | `/overtime/{id}/withdraw` | 申请本人撤回 |
| POST | `/executions` | 原参数追加 `overtime_request_id`，实际日期与批准日期一致 |

加班列表沿用 `execution:view`，申请/执行沿用 `execution:edit`；审批端在登录校验后再次严格检查指定审批人，不需要新增角色或重置既有授权。申请、批准、驳回、撤回、执行填报均写入审计日志，并通过现有通知机制提醒相关人员。启用邮件后，同步加入邮件队列，详见 [公司邮件接入指南](EMAIL_SETUP.md)。

## 维护者验收清单（本次未运行）

1. 普通成员申请工作日晚间 18:00–20:00，确认仅项目经理可审批。
2. 项目经理申请本人项目加班，确认转交部门主管；其他人/申请本人直接调用审批 API 应被拒绝。
3. 正常工作时段、未审批项目、无本人任务权限、汇总任务、重复重叠时段均不能申请。
4. 在批准的加班结束后填报 1.5h：执行列表、任务实际工时、过程报表和首页实际趋势均增加 1.5h；共享看板无新增条目。
5. 申请 2h 后填报 2.5h、0.3h、提前填报或重复新增均应失败；编辑原记录应更新总额。
6. 申请/批准但未填报时可撤回；填报后撤回应被阻止。删除执行记录后可重新填报。
7. 核对假日、调休和北京时间；切换普通执行，确认原预约前置规则未被绕过。
8. 核对并发重复提交、同时审批/撤回，以及任务成员和计划日期调整时的关联保护。

提供了隔离数据库/SMTP 的回归测试源码，但没有运行测试、构建、迁移或启动服务。
