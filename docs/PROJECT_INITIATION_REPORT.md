# 项目立项报告附件

2026-10-09 更新：新建项目必传，扩展 Office 格式；新建 API 改为 multipart，前后端须配套更新。

## 1. 使用方式

1. 打开“项目管理 → 新建项目”，填写项目名称、成员、周期及工时等信息。
2. 在带红色星号的“项目立项报告”选择文件：支持 **Word（DOC/DOCX）、Excel（XLS/XLSX）、PPT（PPT/PPTX）、PDF**，非空文件，单个最大 **20 MiB（界面显示为 20 MB）**。每个项目只有一份生效报告，新建时为**必传**。
3. “保存草稿”和“保存并提交审批”都必须先选择报告、再二次确认。新建项目信息及文件一起提交，项目、成员和报告元数据在同一数据库事务中保存；“保存并提交审批”成功保存后，再调用提交审批接口。
4. 新建时文件格式/大小不合法、存储失败会回滚本次创建，并清理本次新文件，表单及所选文件保留以便重试。若已成功保存并取得 ID，但后续提交审批失败，则重试复用原草稿，不再新建。编辑已有草稿时上传失败，不删除原项目或原报告。
5. 草稿和已驳回项目可以在“编辑项目”补传/替换报告。选择新文件尚未保存时，“取消选择”仅取消待上传文件，不删除已经保存的报告。
6. 在“项目详情 → 基本信息 → 项目立项报告”下载查看；部门主管也可以在“首页 → 待处理事项 → 项目审批详情”下载报告后审批。
7. 待审批、已审批及已完成项目的报告不可替换，避免审批后材料发生变化。此次没有新增附件删除入口。

历史待审批/已审批项目保留原状态及资料，不自动补录或撤销。历史草稿、已驳回项目再次提交审批时必须有报告；后端同时检查服务器文件存在且大小与元数据一致。

**Excel 项目导入**只保存为未生效草稿，不直接送审；到项目管理逐项编辑、上传报告，再提交部门主管审批。模板“填写说明”、导入确认及成功提示均说明这一规则。

如果请求超时，不等于服务器一定没有保存：附件上传失败时会阻止当前表单继续提交审批；如果是提交审批超时，请先刷新列表确认实际审批状态。如果首次创建项目本身超时、尚未返回 ID，也应先检查项目列表，避免重复创建。

## 2. 自动指定的存储位置

原生部署默认路径（相对于后端代码目录，不受启动命令所在目录影响）：

```text
backend/
  storage/
    projects/
      123/
        0123456789abcdef0123456789abcdef.pdf
      124/
        abcdef0123456789abcdef0123456789.docx
```

上面的文件名仅为示例。实际按 **项目的内部数字 ID** 建立文件夹，文件名为服务端生成的 UUID。项目改名不影响文件夹，中文原文件名保存在数据库中，下载时仍使用原文件名。目录首次上传时自动创建，无需提前为每个项目建目录。

本地工作区默认落盘位置示例：

```text
D:/pythonProject/SMIC/project_mangement/backend/storage/projects/123/<UUID>.pdf
```

公司 Linux 服务器部署后，会自动使用该服务器的 `backend/storage/projects/`，不会把本机的 Windows 路径写死到系统。

如需使用独立数据盘，在后端使用的 `.env` 中填写：

```dotenv
# 可省略；默认值如下，相对于 backend/。
PROJECT_FILES_DIR=storage/projects

# Linux 独立数据盘示例（与上项二选一）
# PROJECT_FILES_DIR=/srv/project-management/project-files

# Windows 独立数据盘示例
# PROJECT_FILES_DIR=D:/project-data/project-files
```

- 后端服务运行账号必须对该目录具有创建目录、读写文件的权限，不建议给所有用户开放写权限。
- 修改配置不会自动搬迁已有报告。变更存储盘时，应停止相关写入、按原有目录结构迁移文件并调整权限，再切换配置。
- 多实例/多服务器部署必须使用相同的共享持久化存储，否则上传到 A 节点的报告可能在 B 节点无法下载。本次实现是文件系统存储，不是对象存储服务。

### Docker Compose

`docker-compose.yml` 已为 backend 配置：

```yaml
environment:
  PROJECT_FILES_DIR: /app/storage/projects
volumes:
  - project_files:/app/storage/projects
```

Compose 中该环境变量固定指向持久卷，并覆盖 `.env` 中的同名值，确保不把报告误写到容器临时层。容器重建不会删除命名卷；**不要执行删除数据卷的操作，例如 `docker compose down -v`**。

如果公司要求明确的宿主机路径，可由维护者把上述卷挂载替换为 `/srv/project-management/project-files:/app/storage/projects`。设置宿主机目录权限后再部署；不要只改环境变量却忘记修改挂载。

维护者自行执行，本文档编写时未执行这些步骤：

1. 备份数据库及已有附件目录。
2. 在 `backend` 目录运行：

   ```bash
   alembic upgrade head
   ```

3. 部署配套前端、后端及代理配置；无需额外安装新的 Python/前端依赖，沿用已有 `python-multipart`、标准库及界面组件。
4. 确认附件根目录可写，并按第 6 节自行验收。

项目自带的 `deploy/nginx/default.conf` 已为 `/api/` 设置 `client_max_body_size 25m`，留出 multipart 请求封装空间，应用层仍严格限制单个报告 20 MiB，同时设置上传和代理响应等待时间。**如果公司还有外层 Nginx/网关，外层也需允许这个请求体大小**，否则仍可能收到 413。直接访问后端时，文件大小仍会在服务层分块读取时检查；生产环境应保留网关请求体上限，以避免过大请求在 multipart 解析阶段占用临时磁盘。

不要给附件目录配置 `alias`、`root` 或公开静态文件地址。下载必须经过系统登录及项目访问权限校验。

## 4. 权限、失败处理与保留规则

- 上传：需要 `project:edit` 权限，并遵守现有项目维护范围（项目负责人、部门主管或超级管理员）；项目必须是草稿或已驳回。
- 下载及查看附件信息：需要 `project:view`，并复用现有项目可见范围；知道项目 ID 不代表有权获取附件。
- 上传与提交审批/审批共用项目行锁，避免文件替换与审批并发造成材料不一致。
- 文件名与存储路径分离；扩展名白名单、文件头/Office 容器基本检查、大小检查均在后端执行。DOCX/XLSX/PPTX 分别检查 Word/Excel/PowerPoint 主文档条目，拒绝携带 `vbaProject.bin` 的容器；DOCM/XLSM/PPTM 等未列出的格式不接收。不会执行文档内容或将其解压到磁盘；下载以附件形式响应，并设置 `nosniff` 和禁止缓存。
- 格式检查不是病毒扫描，也不会理解文档内容。旧版 DOC/XLS/PPT 只检查共同的 OLE 文件头，不能据此区分所有旧 Office 内容，也仍可能带宏；PDF 也可能包含主动内容。公司应按安全规范使用终端防护/文件扫描，用户不要随意启用文档宏。
- 写入临时文件后再移动到最终文件名；失败时回滚数据库写入并清理本次临时/新文件。磁盘满或目录无权限会提示检查存储：新建请求中的项目一起回滚，已有项目的补传失败则保留原草稿/报告。文件系统和数据库不是分布式事务，进程被强制终止时仍可能遗留孤立文件，需按备份与运维策略核对；不向页面公开这些文件。
- 替换时生成新的 UUID 文件，数据库只指向最新一份；旧版本文件保留在同一项目目录供恢复，也避免正在进行的下载中断。页面不提供历史版本下载；运维需按公司保留策略备份和定期检查容量。
- 项目软删除后不能再访问附件，但报告及元数据保留，符合当前项目软删除策略。数据库外部物理删除或回滚本次迁移不会自动删磁盘文件，需由维护者按保留制度处理。
- 数据库与 `PROJECT_FILES_DIR` **必须一起备份和恢复**；仅恢复数据库无法找回文件。文件丢失时，下载会给出“检查附件存储或恢复备份”的明确提示。
- Git 和 Docker 构建上下文已排除默认存储目录，避免把公司报告提交到代码仓库或打进镜像；自定义目录也应放在代码仓库及静态资源目录之外。

## 5. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/projects` | multipart，必填 `payload`（项目资料 JSON 字符串）和 `file`（立项报告）；成功后返回项目详情 |
| GET | `/api/v1/projects/{id}/initiation-report` | 返回文件名、大小、上传人和时间；未上传返回 `data: null`，不返回磁盘路径 |
| POST | `/api/v1/projects/{id}/initiation-report` | multipart，单个字段 `file`；上传或替换草稿/已驳回项目报告 |
| GET | `/api/v1/projects/{id}/initiation-report/download` | 携带登录令牌，权限校验后下载原文件 |

新建接口不再接受原先的纯 JSON 请求，以免绕过必传校验。前端使用 `FormData`，让浏览器自动生成 multipart boundary；不要手工设置不带 boundary 的 `Content-Type`。项目编辑仍使用原 JSON PUT 接口，已有草稿的补传/替换沿用独立附件 POST 接口；提交审批接口检查报告元数据及真实文件。每个报告保存到新项目取得的数字 ID 目录下。

`payload` 中字段仍为原有项目字段，如 `name`、`manager_id`、`member_ids`、`department_id`、`budget_hours`、`planned_start`、`planned_end` 等；字段内容先按 `ProjectCreate` 校验，错误返回 422，而不是 500。缺少 `file` 的 HTTP 请求返回 422；服务层直接调用也会拒绝缺少报告的创建。

## 6. 待维护者执行的验收清单

- 创建项目，分别上传有效 PDF、DOC、DOCX、XLS、XLSX、PPT、PPTX；检查服务器对应项目 ID 文件夹、原文件名下载及大小一致。
- 不选择报告点击保存草稿/提交，必须提示必传且不发出创建请求；直接调用新建接口缺少文件也必须拒绝。历史已审批项目详情仍允许显示“暂未上传立项报告”。
- 验证空文件、伪装文件、超 20 MiB、控制字符文件名以及非白名单扩展名被拒绝。
- 模拟新建上传失败，确认项目/成员/报告元数据未提交、新文件已清理，表单保留；若保存成功后提交审批失败，重试不重复创建项目。
- Excel 导入项目应生成草稿，无主管审批通知；未补传附件直接送审应失败，补传后才能送审。验证有元数据但服务器文件丢失/大小异常时同样不能提交审批。
- 草稿/已驳回项目可补传与替换，待审批/已审批项目 API 也拒绝替换。
- 用有权限的项目成员和部门主管下载；用无关账号直接调用附件接口，应返回无权访问。
- 检查首页项目审批抽屉可下载报告；核对操作日志中的项目、文件名及上传人。
- 检查同名文件不会互相覆盖；不同项目文件分开保存。
- 验证 Docker 重建后文件仍存在；备份/恢复目录与数据库后下载正常。
- 检查外部代理不会因默认 1 MB 请求体限制而返回 413。
