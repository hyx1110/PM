# V1.0 → V2.0 升级说明

## 升级前

1. 停止 V1 后端写流量。
2. 备份 MySQL 数据库、`.env` 和部署配置。
3. 记录当前 Alembic revision，应为 `20260909_0001`。
4. 为生产环境设置新的 `IMPORT_DEFAULT_PASSWORD`，不要保留示例值。
5. 准备 Redis；外部通知可以暂不配置。

## 文件与依赖变化

后端新增运行依赖：`openpyxl`、`celery[redis]`、`redis`。前端没有新增依赖，但 `package.json` 和 lockfile 项目版本更新为 `2.0.0`。

维护者自行执行：

```powershell
cd backend
pip install -r requirements.txt
alembic upgrade head
python -m scripts.init_data
```

不要对生产库运行 `alembic stamp head` 代替真实迁移。

## 迁移内容

`20260910_0002_v2_features.py` 会：

- 为 `risk_records` 添加指纹、标题、来源数据、检测/到期/解决时间和唯一索引。
- 新建 `notifications`、`notification_preferences`、`import_jobs`。

V1 已存在的风险记录因 `fingerprint` 可空而兼容；新扫描记录使用非空稳定指纹。

`20260911_0003_safe_deletion.py` 为用户增加软删除字段。`20260911_0004_project_approval_and_work_calendar.py` 会：

- 为项目增加总工时、审批状态、创建人、审批人、审批时间和意见。
- 将升级前已有项目视为已审批，并以“任务预计工时合计”和“已有有效预约工时合计”较大值作为初始额度。
- 新建追加工时申请和工作日历表，写入索引、外键和审计时间。
- 根据国务院正式通知内置 2026 年法定节假日和调休工作日。
- 历史版本曾将系统角色显示名更新为 `L3/L4`，并增加 `calendar:manage` 权限；`0013` 会恢复为“部门主管/职能主管”。

`20260912_0005_personal_time_blocks.py` 会新建 `personal_time_blocks`，保存用户本人的培训、会议、休假、外出、出差和其他时间占用、撤回状态及自动计算工时，并创建用户/时间范围冲突查询索引。

`20260914_0006_employee_profiles_and_role_sources.py` 会：

- 为 `users` 增加唯一 `employee_no`，以已有 `username` 回填并添加二者相等的检查约束；内部自增数字主键保持不变。
- 将手机号长度从 30 扩展至 60，兼容正式人员数据的联系电话长度。
- 新建一对一 `employee_profiles`，保存岗位编号、姓名拆分、职务、地点、成本中心及独立的人事管理职级；升级前用户统一回填为普通员工职级。
- 为 `user_roles` 增加 `is_manual` 与 `is_hr_auto`。升级前已有系统角色全部标记为人工来源，避免迁移后被职级同步误删。

`20260914_0006` 只创建 MySQL 数据结构并回填已有测试账号，不连接正式库，也不导入真实人员数据。

`20260914_0007_business_rules_alignment.py` 会：

- 为部门、组织和人员档案增加 `data_source=local|hrdb`；HRDB 来源数据由业务层按只读处理。
- 为项目增加 `approver_id`，把升级时仍待审批项目的审批人回填为创建人的直属主管。
- 为任务、执行记录和通知增加软删除字段及索引。
- 将旧任务 `pending/confirmed` 规范为 `not_started`，将旧的持久化 `delayed` 规范为 `running`；延期以后仅作为动态展示状态。
- 为没有任何系统角色的历史用户补授 `project_member`，保证每个有效用户至少有一个系统角色。

该迁移不会连接 HRDB 或导入正式数据，也不会自动执行人员同步。

`20260915_0008_project_manager_membership.py` 会为每个缺少对应成员关系的历史项目补写项目经理，项目角色为 `manager`、投入比例为 100%。新代码要求所有预约对象都必须存在当前有效项目成员关系，因此升级现有数据库时必须执行到该迁移。

`20260921_0014_task_hierarchy_and_project_resources.py` 会：

- 将历史任务 `suspended/cancelled` 规范为 `running/not_started`，将执行记录 `paused` 规范为 `running`；
- 为项目成员角色补充 `schedule:edit` 入口权限，服务层仍只允许其预约自己的已分配任务；
- 把 `project_hour_requests` 原表及历史记录重命名保留为 `project_resource_requests`，新增成员增加/移除 JSON 字段；
- 删除 `project_members.allocation_percent`，项目成员不再维护投入比例；
- 为任意层级任务、四种任务展示状态和统一项目资源审批启用新版服务逻辑。

`20260916_0009_simplify_user_schema.py` 按当前用户模型执行最终收敛：

- 保留 `users.id`、`employee_no`、姓名、邮箱、部门、组织、直属主管及账号运行字段；
- 删除 `users.username` 和 `users.phone`；
- 删除 `employee_profiles` 及其中的岗位、人员属性和人事职级；
- 删除 `user_roles.is_manual/is_hr_auto`，现有五类角色关联本身继续保留。

该迁移兼容旧版 MySQL 不支持 `DROP CHECK` 的情况，并在删除表、字段、索引或约束前检查对象是否仍然存在。若 MySQL 因非事务 DDL 在迁移中途失败、但前面的删除操作已经生效，修复代码后可以直接重新执行升级命令，不需要手工重建已经删除的 `employee_profiles` 表。

该迁移会永久移除旧人员档案内容，升级前必须由维护者自行备份数据库。降级只能重建空的旧结构，不能恢复被删除的数据。

`20260916_0010_task_multi_assignees.py` 新建 `task_assignees`，并把所有历史任务的 `tasks.owner_id` 回填为第一条负责人关系。`tasks.owner_id` 暂时保留为兼容主负责人字段，新代码以关联表作为任务编辑权限和“我的任务”范围依据。

`20260917_0011_task_execution_dates.py` 将任务的计划开始/结束和执行记录的实际开始/结束从 `DATETIME` 转换为 `DATE`。迁移使用原值的日期部分，去掉已经不再参与业务判断的小时和分钟；脚本会先检查当前列类型，MySQL 非事务 DDL 中断后可继续执行。

`20260918_0012_permission_status_alignment.py` 会：

- 为部门主管补齐评价权限，为职能主管补齐本人项目维护、预约和评价所需入口权限；
- 移除普通项目成员的项目编辑权限；
- 对未结束、未评价项目中的任务按最新一条未删除执行记录修复状态，重新汇总父任务及开放项目运行态；
- 保留项目手动完成规则，不会因为迁移时任务全部完成而自动关闭项目。

`20260921_0013_remove_project_task_types.py` 会：

- 删除 `projects.project_type` 和 `tasks.task_type` 及任务类型索引；
- 把系统角色显示名统一为“部门主管”和“职能主管”，角色代码保持不变；
- 将现有待审批项目的 `approver_id` 改派为项目所属部门当前配置的部门主管；
- 保留已审批项目状态，不会重新打开历史项目。

`20260922_0015_project_statuses_and_cancelled_cleanup.py` 会：

- 物理删除状态为 `Cancelled` 的历史项目；
- 同步物理删除这些项目的成员关系、资源申请、任务、任务成员、预约、执行记录、评价、风险记录和关联通知；

该迁移的数据删除不可逆。执行前必须备份数据库；降级只能恢复旧状态名称和默认值，不能恢复被物理删除的项目及关联记录。

## 初始化权限

迁移后必须再次执行 `python -m scripts.init_data`。脚本会补齐：

- `risk:view`、`risk:handle`
- `notification:view`
- `import:manage`、`export:download`
- `analytics:view`（兼容旧权限码，现用于隐藏的人员负载汇总 API）
- `calendar:manage`

系统角色的权限会按 V2 默认集合重建，`calendar:manage` 默认授予超级管理员和部门主管。如果生产环境曾直接修改系统角色，请先记录差异，升级后通过角色权限页面重新调整；自定义非系统角色不会被删除。

五类系统角色仍为超级管理员、部门主管（代码 `department_manager`）、职能主管（代码 `functional_manager`）、项目经理、项目成员。所有角色均由项目管理系统直接分配；不再根据人员档案或人事职级自动产生主管角色。

## 升级后的必做业务配置

1. 给普通项目创建人分配“项目经理”角色；直属主管仍用于管理链条和职能主管数据范围，但不再作为项目审批人。
2. 为每个需要创建项目的部门设置一名有效部门主管；所有项目首次审批和项目资源申请都由项目所属部门主管处理。工作日历 UI 已隐藏，日期数据通过后台接口或数据库迁移维护。
3. 检查已有项目自动生成的工时额度，额度为 0 的历史项目如需继续预约，应先由项目经理提交项目资源申请。
4. 每年国务院发布下一年度放假通知后，由维护者通过工作日历后台接口或数据库迁移维护节假日和调休工作日。
5. 抽样确认共享看板中每位用户都能进入“我的时间安排”，并验证个人安排会阻止重叠的项目预约。
6. 以测试数据录入员工号、姓名、邮箱、部门、组织和直属主管，确认三项关系字段指向正确记录。
7. 分别为用户直接分配超级管理员、部门主管、职能主管、项目经理和项目成员，确认角色功能保持不变。
8. 确认没有显式分配角色的新用户获得默认 `project_member`。
9. 确认每个历史项目的项目经理都出现在成员列表且不能移除；新建项目时必须选择至少一名普通成员。
10. 分别用项目经理、部门主管、职能主管和普通成员核对共享看板：项目经理仅见自己的项目组，部门主管见全部人员，职能主管见本人及全部层级下属，普通成员只见本人。
11. 核对项目/任务范围：部门主管/超管全量，职能主管为本人和全部下属相关数据，项目经理/成员为本人负责或参与的数据；成员身份只读。
12. 核对同一任务多条执行记录：任务状态跟随最新有效记录，删除最新记录后回退；全部任务完成后项目仍等待负责人手动确认。

## 回滚提醒

代码可通过版本控制回退；`0016` 降级会删除新产生的项目评价，回退前应先导出；`0015` 删除的历史已取消项目及其关联数据无法通过降级恢复，只能从升级前备份恢复；`0014` 降级会恢复旧表名和投入比例列，但不能还原迁移前的暂停/取消任务与暂停执行状态，也无法把已审批的成员资源变更拆回旧工时单；`0013` 降级可重建项目/任务类型列，但不能恢复历史类型值。`0012` 及更早迁移的数据级回退应优先恢复升级前备份。只有在确认备份可用、相关数据可丢弃时才执行。
