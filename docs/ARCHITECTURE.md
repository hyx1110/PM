# V2.0 架构说明

## 总体结构

```text
Browser
  ↓
Nginx
  ├─ /             → Vue 3 静态文件
  └─ /api、/health → FastAPI ── SQLAlchemy ── MySQL 8
                              │
                              └─ 业务事件写入通知/风险表

Celery Beat ── Redis ── Celery Worker
     │                       ├─ 风险周期扫描
     │                       ├─ 临期提醒生成
     │                       └─ 邮件/企业微信/钉钉投递
     └─ 周期调度
```

核心业务写入仍由 FastAPI 同步完成；外部通知和周期扫描进入 Celery，避免网络渠道拖慢业务请求。站内信直接落库，因此 Redis 或外部渠道不可用时，项目和排期核心流程仍保持独立。

## 后端职责

| 层级 | 职责 |
|---|---|
| `api/v1` | HTTP 参数、鉴权依赖、统一 JSON 或 Excel 文件响应 |
| `services` | 状态机、数据权限、事务、风险规则、Excel 和通知渠道 |
| `repositories` | 分页、关联、聚合和冲突查询 |
| `schemas` | Pydantic 请求与响应结构 |
| `models` | 表、外键、唯一约束、索引 |
| `tasks` | Celery 周期任务入口；调用 Service，不复制业务规则 |
| `core` | 环境、Session、JWT、RBAC、异常、日志 |

## 数据范围

- 项目和任务：所有具备查看权限的用户均可查看；项目仅由本项目经理编辑，任务仅由任务负责人编辑。
- 执行记录：列表可查看，新增/修改/删除只允许记录本人，且新增任务必须由本人负责。
- 日程看板采用独立人员范围：L3/超级管理员查看全部有效人员，L4 查看本人、直属及第二级下属，项目经理查看本人项目成员，普通成员只查看本人；多角色取范围并集。
- 前端隐藏菜单和按钮不是安全边界，后端权限与 Service 数据范围才是。

## 用户身份与 RBAC

```text
users.id（内部数字主键）
├─ employee_no（唯一员工号/登录账号）
├─ name / email
├─ department_id / organization_id / supervisor_id
└─ user_roles ──→ roles ──→ role_permissions ──→ permissions
```

- 超级管理员、L3、L4、项目经理、项目成员是五类完整的系统功能角色。
- `employee_no` 是唯一登录账号；用户表不再保存兼容用户名、手机号、岗位、人事档案或人事职级。
- `user_roles` 只表达直接系统授权，不再记录人事职级自动来源。
- 当前版本只使用 MySQL 数据架构。

## 排期并发与冲突

- 新预约不经过草稿，提交后直接进入 `pending`；只有 `user_id` 对应的被预约人本人可以确认/拒绝。
- 只有项目经理可使用本人负责且已审批的项目预约当前有效成员；L3/L4 行政角色只扩展日程查看范围。
- `pending/changed` 且被预约人尚未确认时，原提交人可以撤回为 `withdrawn`，相应项目额度立即释放。
- `pending/confirmed/changed/running` 参与时间冲突检测。
- `active` 个人时间安排与项目预约双向互斥；培训、会议、休假、外出、出差和其他安排均阻止重叠预约，本人撤回后释放时段。
- 项目预约和个人时间创建先锁定相同的用户记录，再查询两类冲突，避免两个并发事务同时占用同一时段。
- 拖动请求携带读取时的 `expected_version`，服务端版本不一致返回 `40903`。
- 已确认排期移动后变为 `changed`，需要成员重新确认。
- 每次写入递增版本并记录修改前后数据。
- 所有写入口统一调用工作日历与时段校验；预约只能按半小时落在上午或下午工作段内，不能跨午休。

## 项目审批与额度

```text
普通项目经理创建草稿 ──→ 提交给本人直属主管 ──→ 通过/驳回
        │                         │
        └── 无有效直属主管时拒绝提交 └── 驳回后修改重提

项目经理兼具 L3/超级管理员角色 ──→ 系统自动通过

人力预约累计达到额度 ──→ 项目负责人申请追加 ──→ 项目所属部门 L3 审批 ──→ 增加额度
```

项目创建请求必须携带至少一名初始成员。项目保存时，系统在同一事务中写入项目经理的固定 `manager` 成员关系和所选普通成员；历史项目由 `20260915_0008` 回填项目经理关系。任务负责人和所有预约对象因此都可以统一按有效 `project_members` 校验。

普通项目的首次审批人以提交时创建人的有效 `supervisor_id` 为准，并写入 `projects.approver_id`；仅该直属主管本人可以审批，不能由 L3/L4 或超级管理员代批。项目经理兼具 L3 或超级管理员角色时直接通过，避免自己审批自己。追加工时是独立流程，仍以部门表当前 `manager_id` 指向且具有 `department_manager` 系统角色的有效用户为准。预约额度检查锁定项目行，避免并发提交突破总工时。

## 风险引擎

V2 是确定性规则引擎，不是 AI 预测：

1. 查询当前角色可见的人员或项目、开放任务和未来 31 天有效排期：超级管理员/L3 为全量，L4 按两级下属，项目经理按本人项目组，普通成员按本人。
2. 生成任务延期、项目延期、长期未更新、排期冲突、日负载超限候选项。
3. 使用业务指纹查找已有风险；新风险落库并生成通知，已有风险刷新内容和检测时间，已解决但条件仍存在的风险会重新打开。
4. 风险不会因扫描自动删除，需在风险中心进入处理、解决或忽略状态。

## 通知通道

- 站内：通知事件创建时写 `notifications`。
- 邮件：标准 SMTP，可配置 STARTTLS 与认证。
- 企业微信/钉钉：机器人 Webhook 文本消息。
- Worker 只将成功通道写入 `delivered_channels`；失败通道留待后续周期重试。

## Excel 边界

- 模板在请求时由 openpyxl 生成，不在仓库中保存易过期的二进制模板。
- 模板包含固定标题、示例、填写说明和枚举下拉；辅助枚举表设为隐藏。
- 导入明确报告错误，不使用自动纠错掩盖无效数据。
- 导出直接使用数据库可见范围，并保留日期和数字类型。

## 后续扩展边界

MES/EES/YES 集成应放入独立 `integrations` 模块并使用幂等外部键；AI 排期或预测应基于已归档的排期、执行和风险数据形成独立服务。V2.0 未实现这些功能。
